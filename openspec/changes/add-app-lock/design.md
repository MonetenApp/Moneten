# Design

## Context

This change is part of the first build of the app. The build is a Swift package with the modules `Domain`, `Storage`, `Import`, and `App`, as [ADR 0010](../../../docs/decisions/0010-swift-package-and-macos-15.md) describes. Everything runs on the Mac, with no server ([ADR 0002](../../../docs/decisions/0002-local-first-no-server.md)).

The app keeps all accounts, categories, and transactions of the open database in one in-memory `Ledger` (module `Domain`). Every change goes to the database through `Store` (module `Storage`) and then to the ledger. Views read the ledger. This keeps filters, sums, and charts fast for some ten thousand transactions without queries per keystroke.

## Decisions

The first build follows the spec where the task list marks a task as checked. Open tasks keep the behavior of the spec as the target.

### Settings that a program outside the app can change

The settings file of the app in `~/Library/Preferences` is not protected: any program of the user can write it, and macOS does not ask. A setting there must therefore never open the database or weaken the lock.

- Each unlock setting keeps the database password in a Keychain entry of its own: "Moneten database password for automatic unlock", "Moneten database password for Touch ID", and "Moneten database password for Apple Watch". `Vault.PasswordEntry` names them. Only the change on the "Security" tab writes an entry, after the password check, through `Vault.setUnlockMethod(_:on:password:store:)`. Turning a setting off deletes exactly its entry. A shared entry would let a program turn a setting back on without the password: with Touch ID off and the Apple Watch on, the entry of the Apple Watch would also serve Touch ID.
- The entry holds only the password. Whether a setting is on lives in the encrypted database (see "The state of each unlock setting" below), and the user defaults hold no copy of it. The settings file can therefore turn no setting on or off. It is also shared by every data folder, because the app has one bundle identifier, while the Keychain keeps the entries of each database apart under the path of its file. A copy of the toggles in the user defaults let a start with a throwaway data folder, as the debug harness makes, turn the settings of the real database off. The launch reads only the entry of the automatic unlock, so a password stored for Touch ID never opens the database at launch. `Vault.unlockPassword(offered:)` reads the entry of a method that the request offered. A request that offers both Touch ID and the Apple Watch cannot tell which one the user confirmed, so it uses the entry of the first offered method that has one.
- A new database deletes the three entries, because its unlock settings start off. This replaces "a stored password stays" of the design of add-encrypted-database. The random key of a renamed database stays when the new database has a password. A new database without a password replaces it, as the design of add-encrypted-database says under "Create".
- The entry "Moneten database password", which builds before this change shared between all three settings, is deleted at each launch. A user of such a build turns the settings on again.
- The login Keychain of macOS is a file-based Keychain, and it ignores `kSecAttrAccessible` (security review F5). Any process of the user can read an entry after macOS asks, and the app cannot narrow that with an accessibility class. The protection therefore rests on the checks of the app and on the separate entries. Moving the entries to the data protection Keychain, which needs a team signature and an access group, is out of scope for this change.
- `Keychain.write` removes an entry of the same service and account first and then adds a new one (issue #399). An update would keep the access list of the entry it finds. Another program of the user can create an entry in advance with an access list that lets every app read it, because the service names are fixed and the account is the path of the database file. The app would then write the password into it, and the program could read it without a prompt. A new entry gets the access list that macOS gives it by default, which names only the app that created it. When the add fails after the removal, the entry is gone and `write` throws the error of the Keychain. A password change and an unlock with the password write every entry before they throw the first error, so no entry keeps an earlier password because a later write did not run. A password change then reports `keychainNotUpdated` and an unlock shows the Keychain error. In both cases the vault turns off, in the database, each setting whose entry is gone, so the toggle shows it as off. It learns that from the attributes of the entry, never from a password. An unlock rewrites an entry only after it read it and found another password. A read that fails, such as the one of a locked login Keychain whose prompt the user canceled, throws before anything changes: a delete works on a locked keychain, but the add does not, so a rewrite would turn every setting off. The tests give `Vault` a keychain file instead of the keychains of the user. `Keychain` checks before every step that the file exists and throws otherwise, because macOS adds an entry for a keychain without a file to the default keychain of the user.
- Every Keychain entry of the app lives in the login keychain of the user, which `Keychain` opens by its path `~/Library/Keychains/login.keychain-db` before each step (issue #419). An add names it with `kSecUseKeychain`, and a read, a delete, and a check for an entry search only it with `kSecMatchSearchList`. Without that, an add goes to the default keychain and a read searches the search list of the user, and a program of the user can change both without a prompt: it creates a keychain whose password it knows, makes it the default and the first of the search list, and plants a stale entry for a setting that is on. The next unlock with the password would then rewrite that entry with the real password, and a new database without a password would store its random key there. The home folder comes from the user database of macOS through `getpwuid_r`. `NSHomeDirectory()` and `NSHomeDirectoryForUser(_:)` follow the environment variable `CFFIXED_USER_HOME`, which the program that starts the app sets (`open --env`), and the hardened runtime removes only the `DYLD_` variables. With them, a program could point the app at a home folder of its own, with its own keychain file at the path of the login keychain. Without a home folder in the user database, every step throws, and nothing falls back to Foundation. `SecKeychainOpen` is deprecated together with the file-based Keychain, but no other call returns the login keychain: `SecKeychainCopyDomainDefault` returns the default, which is what the program changes. When the file is missing, every step throws `Keychain.Failure` with the path, and the vault reports it as a Keychain error. Nothing falls back to the default keychain. The protection is that the path is no longer optional: the app always passes the login keychain, which a test checks against the user database. The other tests give `Vault` and `Keychain` the path of a keychain file in a temporary folder in place of the login keychain, and they plant an entry of the same name in a second file, which no step may touch. That file is never the default keychain or in the search list, because no test reads or changes the keychains or the search list of the Mac that runs it. A reproduction of the attack itself needs a disposable macOS account or virtual machine and is not part of the suite. Limits: `Keychain` checks that the file exists, not that it is the keychain macOS unlocked at login, and a step can race the check. A program of the user can still replace the file of the login keychain, or put a symbolic link to a keychain of its own at its path. Both take every other password of the user out of reach of every other app, so the user notices. The data folder in `~/Library/Application Support` still follows `CFFIXED_USER_HOME`, which a separate issue fixes. The data protection Keychain with an access group, which needs a build signed with a team, stays the later step. It also makes `kSecAttrAccessible` take effect. No release stored an entry in another keychain, so no entry moves.
- Debug and Perf builds read `MONETEN_KEYCHAIN_PATH`, the path of a throwaway keychain file that takes the place of the login keychain for `Vault` and the crash report key (issue #421). The app reads it only under `#if DEBUG || PERF_HARNESS`, as `MONETEN_DATA_DIR`, and passes it to `Vault(folder:version:keychainOverride:)` and `CrashReportStore(folder:keyInFolder:keychainOverride:)`, because Xcode builds the package without the compilation conditions of the app. A Release build passes nil, and `scripts/build-app.sh` fails a Release build in which any Mach-O file holds the name of the variable. A run of the debug harness (`MONETEN_DEBUG_DIR`) exits with status 2 at launch, before anything opens a data folder or a keychain, unless it also has `MONETEN_DATA_DIR` and `MONETEN_KEYCHAIN_PATH`. Without a keychain file of its own, a check could read or write the login keychain of the developer. Without a data folder of its own, the unlock with the password would find no entry in the empty throwaway file and turn off automatic unlock, Touch ID, and Apple Watch in the real database, `CrashReportStore` would find no key for the real `CrashReport.encrypted` and delete it, and a real database with a random key would not open. `HarnessRun.missing(debugFolder:dataFolder:keychainFile:)` in Storage holds this rule, so that a test checks it, and the app names the variables, so that a release build holds no name of them. The app reads an empty variable as a missing one, and the libraries take a given path as it is. A run with `MONETEN_KEYCHAIN_PATH` but without `MONETEN_DATA_DIR` exits with status 2 too, also without the harness, because a developer who starts a debug build by hand to check automatic unlock would otherwise unlock the real database against the empty file. A debug build started without the harness and without the variable keeps the real data folder and the login keychain, so a developer can still check the real path. `scripts/check-debug-log.sh` and `scripts/perf-check.sh` create the file with `security create-keychain` on its path, which changes neither the default keychain nor the search list, and remove it as a plain file at the end. With the variable, the crash report key goes into that file also when the run has its own data folder.
- An unlock with the password replaces the entry of a setting that is on when it holds another password, as before, but never creates one. Only the "Security" tab turns a setting on.
- "Lock when main window is closed" and "Lock after inactivity" live in the table `lockSetting` of the encrypted database, one row that `Store.lockSettings()` reads and `Store.saveLockSettings(_:)` writes. A database without the row has the defaults: off, and 10 minutes. The settings matter only while the database is open, so the app reads them at each unlock. The complete export leaves them out.
- No data moves from the user defaults: no release has the old layout.
- Debug and Perf builds keep the inactivity lock off with `MONETEN_DEBUG_NO_IDLE_LOCK=1`, which the scripts of the debug harness set. Release builds do not read the variable.

### The state of each unlock setting (issue #405)

Before this change a setting was on exactly while its Keychain entry existed. Any program of the user can create an entry with the fixed service name and the path of the database file as account. With "Unlock automatically at application start" off, a program created that entry with any text. The next unlock with the password found an entry with another password and replaced it with the real one, under the access list of the app, and from then on the database opened at every launch without a password.

- The table `unlockMethod` of the encrypted database holds one row for each unlock setting that is on, by the raw value of `Vault.PasswordEntry`. `Store.unlockMethods()` reads it and `Store.saveUnlockMethods(_:)` writes it. A database without rows has every setting off. Another program cannot write the database without its password, so it cannot turn a setting on. A separate table keeps the row of `lockSetting` as it is: `Store.saveLockSettings(_:)` replaces that row whole.
- `Vault.setUnlockMethod(_:on:password:store:)` changes both. Turning a setting on writes the entry first and then the row; when the row fails, the vault deletes the entry again, and an entry that stays anyway never counts. Turning a setting off writes the row first and then deletes the entry. With the other order, a crash between the two steps would leave the setting on without its entry, and a program could plant the entry before the next unlock with the password, which would then write the real password into it. With "off" written first, a delete that fails or never runs leaves an entry that never counts, and the next unlock deletes it. A failed delete therefore leaves the setting off, and the "Security" tab says that the password stays in the Keychain until the next unlock with the password.
- An unlock with the password calls `Vault.refreshStoredPassword(_:on:)`. It deletes the entry of each setting that is off, without reading it. It reads the entry of each setting that is on and replaces it when it holds another password, as before. A setting that is on and has no entry, such as after a write that the Keychain refused, turns off in the database, so the toggle shows what works. The deletes come first: they need no read, and a read that fails stops only the rewrites.
- The launch cannot read the database before it opens it, and only the entry of the automatic unlock can open it. So the launch still tries that entry when it exists, through `Vault.open(storedFor:password:upgrading:)`, and confirms the result against the database right after the open. Touch ID and the Apple Watch take the same path. The check takes every setting that the request offered, not only the one whose entry gave the password: a request that offers Touch ID and the Apple Watch does not say which one the user confirmed, so with Touch ID on, the Apple Watch off, and a planted entry of the Apple Watch, a confirmation on the watch would otherwise unlock with the real entry of Touch ID. When any offered setting is off, the vault closes the database and throws `Vault.Failure.unlockMethodOff` with the settings that are on. The app then shows the lock screen with a notice and offers only the settings that are on and have their entry, and nothing of the database reaches the window. In both outcomes the vault deletes the entries of the settings that are off. A failed delete changes nothing there, and the notice does not claim that the entry is gone. A marker outside the database that says whether to try the entry would not help: any program of the user can write it as well, and the check after the open is what decides.
- Before the first unlock of a launch the lock screen offers Touch ID and the Apple Watch when their entries exist, because only the entries are readable then. A planted entry therefore shows a button, but its confirmation runs into the check above. After the first unlock the app keeps the state of the database, and a lock during the session offers only the settings that are on there.
- No state comes from the Keychain. Migration `v30` creates the empty table, so a database from before this change has every setting off, whatever entries exist. Reading an existing entry to set the state would trust exactly the entry that another program may have planted, and the hole would stay open for every installation that updates. The first unlock after the update deletes the entries, and the user turns the settings on again once. No release has shipped, so only databases of development builds lose the setting, and the cost is one switch per setting.

### Sheets across a lock (issue #482)

The lock closes the open sheet of the main window, because the main window shows only the lock screen, and the unlock shows the sheet again with the input from before the lock.

- `HeldSheet` in `Domain` holds the input. Each sheet with input writes it at every change and when it opens, through the view modifier `keepsInput(_:of:)`, so the input is in memory before the lock closes the sheet. The input lives only in the memory of the app: never in the database, the preferences, or the Keychain. It ends with the process.
- The input belongs to the database file that was open at the lock. `Vault.databaseStamp()` reads the device, the inode, the size, and the times of change of the file, and whether the WAL, the shared memory, and the rollback journal of SQLite exist, with their sizes and times of change. It takes the stamp once at the lock, after the store closed, and once after an unlock with the password opened the store, so the second stamp names the file that the store reads. An open writes nothing, so the stamps match when nothing changed. The sheet returns only when both stamps are the same. A backup that took the place of the database while the app was locked, also one copied over the file in place with its old time of change, one that came between the start of the unlock and the open, and a restored side file such as a WAL, get no input of the database before it. A change after the second stamp is a change on disk of the open store, which closes the database and drops the input. A change of the metadata alone, such as a new extended attribute, moves the time of change too and drops the input, which is the safe side. A launch, "Try Again", a new database, a failed unlock, and every close that is not a lock drop the input.
- The lock only moves the input inside `HeldSheet`, which no view observes. The lock screen therefore comes in an update that changes nothing else that a view reads (issue #151).
- The unlock decides which sheet returns, before the main view draws, and `AppModel.returningSheet` names it until the sheet opens. The alerts count it as a sheet, so an alert that waited across the lock shows only after the sheet closes (`SheetAlerts`, issues #217, #218, and #300). The main view opens the sheet one turn after it appears. The sheet takes its input after it loaded the stored values. SwiftUI can show the sheet twice after the unlock, the first time with the state from before the lock and the second time with new state, which is the one on screen, so the input stays for each appearance until the sheet closes. Any later opening starts from the database. A sheet whose subject is gone stays closed, and its input goes.
- A new transaction keeps the account it was started in. When the unlock selects another account, for example after a click on a notification of that account, the sheet stays closed and its input goes, so the input never lands in another account. A new category returns only while the group it goes into is still a group.
- The date fields keep their text as typed, also while it is not a date yet.
- The account settings merge the input with the account as it is at the time of saving (`Account.takeSettings(from:opened:)`), as for a refresh that ends while the settings are open.
- The account settings, the calibration, the account group settings, the category settings with the rule, a new or edited transaction, a comment, a split, a new category, and the name sheets (new account group, save search, rename search) keep their input. A split that runs at the lock stores nothing, and the window shows again with its amounts. The sheets for a password, "Add Account", the migration, the file import, the export, ⌘K, and "Undo Split" do not come back: the password sheets must not keep a password, and the lock cancels the work of the others.
