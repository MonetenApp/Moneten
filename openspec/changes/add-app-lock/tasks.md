# Tasks

One task per requirement of the spec. A task is checked only when a test or a check in the running app shows the behavior.

## 1. Requirements

- [x] 1.1 Ask for the password at launch. Verified by debug harness: a wrong password stays locked, the right one unlocks.
- [x] 1.2 Lock by command. Verified by ⌃⌘L, the menu command, and the toolbar button call AppModel.lock; checked with the debug harness.
- [x] 1.3 A locked app shows no data. Verified by the main window shows only the lock screen, see the debug harness snapshot in the first build.
- [x] 1.4 Locking closes the database. Verified by AppModel.lock closes the store and empties the ledger.
- [x] 1.5 Lock when the main window closes. Verified by the debug harness: with the setting on, "closemain" and "openmain" show the lock screen (phase locked). The setting is off by default (#269).
- [x] 1.6 Lock after inactivity. Verified by the debug harness: with "Lock after 1 minute of inactivity" and no input, the app locked 74 seconds after the unlock (the check runs every 20 seconds). The setting is on with 10 minutes by default (Settings snapshot of a new installation). The wake check compares the clock, so time asleep counts; a real sleep of the Mac was not part of the check (#269).
- [x] 1.7 Unlock automatically at launch. Verified by the debug harness: with the setting on and the password in the Keychain, the next launch opens the main window without a prompt. A Keychain error or a stored password that no longer opens the database leads to the lock screen with the reason, and the unlock with the password stores it again (#266). The launch reads only the Keychain entry of the automatic unlock, which only the settings write: AppLockStorageTests "A password stored for Touch ID does not unlock at launch", and the debug harness: with only Touch ID on, a settings file changed to turn on the automatic unlock leaves the lock screen and the toggle off (#269). A start with another data folder leaves the settings of this database alone: AppLockStorageTests "A database in another data folder without entries leaves the entries of this database alone", and the debug harness: a new database in a throwaway data folder, then the next launch of the first folder unlocks without a prompt (#269).
- [ ] 1.8 Unlock with Touch ID. Built: its own setting "Unlock with Touch ID"; the lock screen asks at once and keeps "Open with Touch ID" for another try after a cancel. Verify it in the app with a registered finger.
- [ ] 1.9 Unlock with Apple Watch. Built: its own setting "Unlock with Apple Watch"; with both settings on, one request offers both and the button reads "Open with Touch ID or Apple Watch". Verified: without a watch in range the lock screen shows "No Apple Watch was detected nearby." and the password field, in the debug harness. Verify the confirmation on a watch.
- [x] 1.10 The password always unlocks. Verified by the debug harness: with "Unlock with Apple Watch" on and no watch nearby, the lock screen shows "No Apple Watch was detected nearby." and the password field, and the password unlocks. A Keychain error or a stored password that no longer opens the database also leaves the password field with the reason (#266, #269).
- [x] 1.11 Unlock settings keep the password in the Keychain. Verified by the debug harness command "security", which runs the change of the password prompt: turning on "Unlock automatically at application start" stores the password, turning on Touch ID and then off the automatic unlock keeps it, and turning off the last setting deletes it (#269). Each setting has its own entry: AppLockStorageTests "Turning a method off deletes only its entry", "The settings are the entries: turning a setting on or off shows in the toggles, and only an entry unlocks", and "A wrong password changes no entry", and the debug harness: turning off the automatic unlock with Touch ID on keeps the entry of Touch ID, and the next launch asks (#269).
- [ ] 1.12 Report a Keychain failure. Built: a failed store leaves the setting off, and a failed delete leaves the last setting on, each with the error of the Keychain under the settings. The lock screen shows a Keychain error of the automatic unlock (#266, #269). Verify it in the app with a Keychain that refuses the entry.
- [x] 1.13 The Keychain entry follows a password change. Verified by OpeningTests "A restored backup with an older password replaces the newer password in the Keychain after the unlock", whose change of the password replaces the stored one. A change that the Keychain does not accept is reported, and the next unlock with the password stores it again (#266). Every entry follows: AppLockStorageTests "A password change replaces each stored entry, and an unlock replaces a stale entry but creates none" (#269).
- [ ] 1.14 Explain why Touch ID is not available. Built: separate messages for a Mac without a sensor, no registered finger with "System Settings → Touch ID & Password", a lockout after failed attempts, and a closed lid; the setting stays off. Verify each message in the app.
- [ ] 1.15 No Touch ID request while the lid is closed. Built: the lock screen starts a request only for methods that macOS reports as usable, so a closed lid leaves the password field and the Apple Watch. Verify it with a closed lid on an external display.
- [ ] 1.16 Explain why the Apple Watch is not available. Built: turning the setting on without a watch approved in macOS names "System Settings → Touch ID & Password" and leaves the setting off. Verify it in the settings.
- [ ] 1.17 Clear a typed password after five minutes. Built: the lock screen clears the field 300 seconds after the last change of its text. Verify it in the app; the debug harness cannot type into the lock screen.
- [x] 1.18 Security settings need the password. Verified by the debug harness command "security": a wrong password leaves "Lock when main window is closed" off and "Lock after inactivity" at 10 minutes, and the right one changes them. Every toggle and the picker of the tab open "Enter Database Password" first (settings snapshot) (#269). The lock settings live in the encrypted database: AppLockStorageTests "The lock settings stay in the encrypted database across a reopen", and the debug harness: with both lock settings on and the settings file changed to turn them off, closing the main window and 85 seconds without input each lock the app (#269).
- [x] 1.19 A locked app does no work with the data. Verified by AutoRefreshTests "A locked app runs nothing, and the unlock runs the accounts that became due meanwhile". The lock cancels refreshes, a rule run, a file import, and an export, and closes the database. Statements and automation requests do not exist yet (#269).
- [x] 1.20 Help for a forgotten password. Verified by "Forgot your password?" on the lock screen.
- [x] 1.21 Lock needs a database password. Verified by lock command and button are disabled without a password.
- [x] 1.22 A secret goes only into a Keychain entry of the app (#399). Verified by KeychainTests "A write never puts the value into an entry that another program created, so the access list of that entry is gone", against a keychain file that the test creates, which failed before the fix. Verified in a debug build with a throwaway data folder: entries for automatic unlock and Touch ID planted with an access list for every app named only Moneten after the "security" harness command turned each setting on, the next launch unlocked without a prompt, and turning both off left no entry. The Keychain that refuses the add after the delete: AppLockStorageTests "A password change that the Keychain refuses writes every entry, so none keeps the earlier password", with a locked keychain file and two settings on, which failed while the writes stopped at the first error; the unlock uses the same `writeEach`. A locked Keychain at an unlock: "An unlock whose Keychain cannot read an entry, such as a locked one whose prompt the user canceled, keeps every entry and setting", which failed while an unreadable entry counted as stale. After either failure `AppModel` reads the settings again; the app has no unit tests, so that line is checked by reading it. All tests of the vault use keychain files from `StorageTestSupport`, run in CI, and leave the login Keychain unchanged. A keychain file that does not exist, or that was deleted after it was opened, refuses every step: KeychainTests "A keychain file that does not exist refuses every step, so nothing goes into another keychain" and "A keychain file that was deleted after it was opened refuses every step", which failed for read, contains, and delete before the check (the write was not run against the old code, which would have written into the login Keychain).
- [x] 1.23 The database holds the state of each unlock setting (#405). Verified by AppLockStorageTests against keychain files of their own, where the `security` tool plants entries as another program: "An entry that another program created for a setting that is off goes at the unlock and never takes the password", "An entry of a setting that is off that opens the database at launch closes the database again and goes", "Touch ID with an entry that another program created while the setting is off leaves the database closed", "A database from before the unlock state has every setting off, whatever entries the Keychain holds" (it drops the table and the record of migration `v30` and reopens), and "A setting that is on and whose entry is gone turns off at the unlock". Round 1 of the merge gate: "A request that offered Touch ID and an Apple Watch that is off leaves the database closed, also with the real Touch ID entry", "An unlock with the automatic unlock deletes the entries of the settings that are off", "Turning a setting on whose state the database refuses removes the entry again", "Turning a setting off writes the state before it deletes the entry, so a failed delete leaves the setting off", and "A password change never writes the new password into an entry of a setting that is off". The tests of the settings, the password change, and the locked Keychain now check the state in the database next to the entries. Verified in a debug build with a throwaway data folder: an entry planted with the `security` tool while the setting was off was gone after the launch, and the unlock with the password left "Unlock automatically at application start" off with no entry. Turning it on unlocked the next launch without a prompt, and turning it off made the next launch ask. A backup copy from before turning it on, put in place of the database, made the launch with the entry of the app show the lock screen with "The Keychain holds a password for an unlock setting that is off for this database, so the password does not unlock Moneten." and left no entry. With automatic unlock on and an entry of Touch ID planted while Touch ID was off, the launch unlocked without a prompt and the Touch ID entry was gone. A Touch ID or Apple Watch confirmation needs a finger or a watch and was not checked in the app; the check after the open is the same one, and the tests cover a request that offered both.
- [x] 1.24 Keychain entries stay in the login keychain (#419). `Keychain` takes the path of its keychain file from the caller and opens it before each step: an add names it with `kSecUseKeychain`, and a read, a delete, and a check search only it with `kSecMatchSearchList`. `Vault(folder:)` and the crash report key pass the login keychain in the home folder of the user database (`getpwuid_r`), which `CFFIXED_USER_HOME` and `HOME` do not change. Without a home folder every step throws. The protection is this path, which is no longer optional, and LoginKeychainTests "The vault of the app uses the login keychain in the home folder of the user database" checks it against `getpwuid`. Before the fix the vault of the app had no keychain file, so its entries went to the default keychain. The other tests check that a step touches only the file it was given, with a throwaway file in place of the login keychain and a second throwaway file that holds an entry of the same name: "Every step of an entry uses only its keychain file and never touches an entry of the same name in another keychain", "An unlock with the password rewrites a stale entry only in the login keychain, never in another keychain with an entry of the setting", "A login keychain that cannot be opened stores no secret anywhere and says why", and KeychainTests "Without a home folder in the user database every step refuses and names the login keychain". The second file is never the default keychain or in the search list, because no test may change the keychains of the Mac. Most of these tests would also pass on the old code, whose test mode already gave a file. A reproduction of the attack itself needs a disposable macOS account or virtual machine and is not part of the suite. The tests of #399 and #405 pass unchanged apart from the path. `ls -lT ~/Library/Keychains/` was the same before and after the run of the storage tests. In a debug build with a throwaway data folder, the next launch after turning on "Unlock automatically at application start" unlocked without a prompt. That check wrote an entry into the real login keychain, which the rules no longer allow; it was turned off again, and later checks wait for a keychain override in debug builds. The errors of a missing login keychain and of an unknown home folder are checked in the tests only.
- [x] 1.25 Debug and Perf builds take a throwaway keychain file from `MONETEN_KEYCHAIN_PATH` (#421). The app reads the variable only under `#if DEBUG || PERF_HARNESS` and passes it to `Vault` and the crash report key. LoginKeychainTests "The vault and the crash report key use the keychain file of the override, and the login keychain without one" checks the libraries. The scenario "An environment variable names another keychain file" holds because a Release build passes no override: `scripts/build-app.sh` fails a Release build in which any Mach-O file of the bundle holds the name of the variable. The Release build held no `MONETEN_` name at all, and the check failed on the Debug build, whose `Moneten.debug.dylib` holds it. A run of the debug harness keeps to its own data folder and keychain file: HarnessRunTests "A harness run starts only with a data folder and a keychain file of its own", "A run without the debug harness and without a keychain file of its own starts", and "A keychain file of its own needs a data folder of its own, also without the harness" check `HarnessRun.missing`, which did not exist before round 1 of the merge gate, when a harness run with the real data folder and a throwaway keychain file started. A Debug build started with `MONETEN_DEBUG_DIR` and `MONETEN_KEYCHAIN_PATH` but without `MONETEN_DATA_DIR` exited with status 2 and named the variable, and the file list and the times of change in the real data folder were the same before and after. A run without `MONETEN_KEYCHAIN_PATH` exited the same way. `scripts/check-debug-log.sh` passed, and the keychain file of its run held the crash report key and the password of "Unlock automatically", which the script now checks. `scripts/perf-check.sh` passed. `~/Library/Preferences/com.apple.security.plist` did not exist before or after the runs, so the search list and the default keychain did not change. `login.keychain-db` did change during the first session, from 705352 to 707520 bytes, but by processes other than Moneten: the unified log showed commits by `assistantd`, `sharingd`, and Sparkle's `generate_keys`, which the owner ran from another worktree, and every commit of a Moneten process went to a throwaway file. In round 2 it changed again, with the same size and a new time of change: the unified log showed commits by `sharingd`, Google Drive, and `assistantd` only, and the three commits of Moneten went to the keychain files of `check-debug-log.sh` and `perf-check.sh`.
