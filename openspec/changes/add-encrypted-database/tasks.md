# Tasks

One task per requirement of the spec. A task is checked only when a test or a check in the running app shows the behavior.

## 1. Requirements

- [x] 1.1 All personal data is in one encrypted database. Verified by VaultTests "The file shows no readable data".
- [x] 1.2 The database password is the key. Verified by VaultTests "The database password is the key".
- [x] 1.3 Offer a password at first launch. Verified by the debug harness snapshot in the first build.
- [x] 1.4 A database without a password uses a random key. Verified by OpeningTests "A database without a password opens with the random key, and the file alone does not open elsewhere" and the sidebar hint, which opens "Set Database Password...". An ad hoc rebuild cannot read the key, see ADR 0010 (#266).
- [x] 1.5 Set a password later. Verified by OpeningTests "Setting a password later keeps the data and removes the random key from the Keychain" with 3 accounts. A key or marker that could not be removed is reported, and the app still knows that the password is set. The copies take the password before the random key goes: OpeningTests "Setting the first password encrypts the copies in the database folder before the random key goes", "A copy that cannot take the first password keeps the random key in the Keychain and is named", and "A first password that stopped after the database took it is finished at the unlock with the password" (#266).
- [x] 1.6 The new password is entered twice. Verified by the debug harness snapshot in the first build.
- [x] 1.7 Show the strength of a new password. Verified by the form shows the grade while the user types.
- [x] 1.8 Warn that a forgotten password cannot be recovered. Verified by the debug harness snapshot in the first build.
- [x] 1.9 Change the password. Verified by VaultTests "Change the password". The copies in the database folder follow the change: verified by OpeningTests "A password change encrypts the copies in the database folder again, so the earlier password opens none of them" (#266).
- [x] 1.10 A failed password change leaves the database usable. Verified by OpeningTests "A password change that fails on the disk keeps the current password, and later saves still open with it", "A password change that a reader of another program stops leaves the copies and the Keychain with the current password", and "A first password that fails on the disk keeps the random key, and later saves still open with it". The first and the third fail without the fix: the save after the failed re-key left a file that neither password opened. Round 2 of the merge gate: OpeningTests "A first password without the random key in the Keychain changes no key", "A first password whose result no fresh connection can read refuses every later write", "A reader of another program in WAL mode stops the password change", "A password change takes a file in WAL mode back to the rollback journal first", and DatabaseGuardTests "A commit of another program right before the re-key stops it, and the commit stays", each failing without its fix.
- [x] 1.11 No way around the password. Verified by VaultTests "Many wrong attempts change nothing".
- [x] 1.12 Show progress while the database opens. Verified by the debug harness: a database of layout v16 with 50,000 transactions shows "Upgrading database..." on the lock screen after the password, then the main window (#266).
- [x] 1.13 Check the integrity of the database when it opens. Verified by OpeningTests "A damaged index is reported, the next open repairs it, and a copy of the damaged file stays", "A damaged table that the repair cannot read asks for a backup copy and creates no new database", "A backup that the user put in place of a damaged database needs no repair", and "A repair that worked is not reported as failed when its marker cannot be removed", and by the debug harness with a damaged page (#266).
- [x] 1.14 Upgrade the database safely. Verified by OpeningTests "An upgrade keeps a backup copy of the old state and opens the upgraded database with all data", "A failed upgrade leaves the database unchanged and removes the temporary copy", "An upgrade keeps the rows that an earlier version saved right before a stop", "An upgrade waits while another program has the database open, and loses none of its rows", and "An upgrade removes an old journal next to its work file before it makes the copy" (#266).
- [x] 1.15 Refuse a database from a newer version. Verified by OpeningTests "A database that a newer version upgraded is refused with both versions, and the file stays unchanged" and "A newer database that waits for a repair is refused before the repair changes it". A database upgraded before this change has no recorded version, and the message then names only the running version (#266).
- [x] 1.16 Only one running copy uses the database. Verified by DatabaseGuardTests "A second opener of the same data folder is refused until the first one lets go" and "The system releases the lock of a copy that ends without letting go", and in a debug build: a second copy from another folder on the same data folder showed "The database is in use by another application.", its `create` changed nothing, and the database file and the crash report file kept their bytes. After the first copy was killed, a new copy opened the database.
- [x] 1.17 Detect a change of the database on disk. Verified by DatabaseGuardTests (a replaced file, an older copy written in place, a write of another program, own writes that never count, and loading again), and in a debug build: a file moved into place of the open database showed "The database has been changed on disk, outside of Moneten." at once, the file kept the bytes of the replacement, and "Load Database Again" opened it through the lock screen.
- [x] 1.18 Explain every problem with the database file. Verified by OpeningTests "Each problem with the database file has its own message with the path": an empty file, a folder, a write-protected file, a folder without write permission, and a folder with files but no database, which starts no new database; and "Opening never creates the database file, even when it went away while the app was locked" (#266).
- [x] 1.19 Mention the automatic backup copy when the database cannot be opened. Verified by OpeningTests "A failure to open names the automatic backup copy and how to restore it" (#266).
- [x] 1.20 Do not open a database file from the Finder. Verified by DataFolderTests "A database file from the Finder is told apart from other files, whatever its name and case", and in a debug build: `open -a` with a copy of the database file showed the alert "Database file", and the app stayed unlocked with its own database.
- [x] 1.21 Copies in the database folder follow a password change. Verified by OpeningTests "A password change encrypts the copies in the database folder again, so the earlier password opens none of them", "A copy that another program has locked stops the change, and the old password still opens everything", "A password change that stopped after the database took the new password is finished at the next start", and "A password change that stopped before the database changed keeps the copies with the old password" (#266).
- [x] 1.22 A copy in use stops the first password. Verified by OpeningTests "A copy that another program has locked stops the first password, and the random key still opens everything" (#266).
- [x] 1.23 Work files go before a password change. Verified by OpeningTests "A work file that cannot be removed stops the password change before the database changes", "A work file that cannot be removed stops the first password before the database changes", and "A password change removes the journal of a work file whose work file is already gone" (#266).
- [x] 1.24 Deleted data leaves no trace in the database file. Verified by SavedPINTests "A removed PIN leaves no byte in the decrypted pages, also after the password changes" (#332) and "A PIN removed through a connection with only the key, as before secure_delete, leaves no byte in the database, its upgrade backup copy, or a backup" (#335).
- [ ] 1.25 A new database never uses a key from the Keychain (#399).
