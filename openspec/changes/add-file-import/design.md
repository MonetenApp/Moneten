# Design

## Context

This change is part of the first build of the app. The build is a Swift package with the modules `Domain`, `Storage`, `Import`, and `App`, as [ADR 0010](../../../docs/decisions/0010-swift-package-and-macos-15.md) describes. Everything runs on the Mac, with no server ([ADR 0002](../../../docs/decisions/0002-local-first-no-server.md)).

The app keeps all accounts, categories, and transactions of the open database in one in-memory `Ledger` (module `Domain`). Every change goes to the database through `Store` (module `Storage`) and then to the ledger. Views read the ledger. This keeps filters, sums, and charts fast for some ten thousand transactions without queries per keystroke.

## Decisions

The first build follows the spec where the task list marks a task as checked. Open tasks keep the behavior of the spec as the target.

- `TransactionFileImporter.parse` (module `Import`) returns a CAMT entry with the status PDNG or FUTR as pending, on the booking date of the entry, and leaves out an entry with the status INFO. A pending row from a file is booked by `reconcile` (module `Domain`) like one from a refresh, by the rule of `add-account-refresh`: a later file or refresh brings a booked row with the same amount and the same counterparty, at most seven days apart, and `Bookings` pairs it with the stored pending row. The counterparty is the IBAN when both rows have one, otherwise the name. The booking date stays the date of the entry, so the booked version lies within the seven days.
- The CAMT reader builds one transaction per `Ntry` with the amount of `Ntry/Amt`, as the first build does. It does not split a batch into its transaction details. The first build overwrites the name, the IBAN, the BIC, and the references for each `TxDtls`, so a batch takes the counterparty of its last payment. The reader instead collects the values of all details and keeps a counterparty field only when every detail gives the same name and IBAN. For such a batch it keeps a reference only when every detail gives the same value. A batch to several counterparties has no references. It already joins the `Ustrd` purposes of all details.
- The CAMT reader reads the return reason from `RtrInf/Rsn/Cd`. `Transaction` gets the field `returnReason` through a new migration in `Sources/Storage/Schema.swift`. `Transaction(arriving:in:fetched:)` and `takingBankFields(of:)` in `Sources/Domain/Reconcile.swift` copy it, so a stored or booked row keeps it.
- `Domain` keeps main's booked-only `partners` path unchanged. The scoped overload collects new-rule candidates only for pairs with a pending side or a stored `fileIdentity`. A booked-only refresh without file identities in its day window or identity lookups calls main's function directly. Indexes cover delivered days plus seven days on each side and matching source IDs or file identities. A reference lookup also preserves historical pending echoes across successive date changes. Stable positions are computed only for candidates. In mixed histories, that same function checks each booked legacy edge, with no preselected partners. All viable edges enter the shared pool with their actual slot, fit, and distance. Legacy edges keep main's input positions. It uses the five numbered levels in "Order-independent pending pairing" in the spec. One tuple orders level, current versus historical version, live versus deleted identity partner, fingerprint fit, day distance, and stable delivered and stored positions. The original file identity and source ID share one level. Fingerprint fit is exact, compatible, or absent, as stated in the spec. Stable tombstone positions compare persisted fields as tuples, including optional-value presence.
- Real source IDs and nonempty end-to-end references must agree. A file fingerprint includes date and purpose, so its disagreement does not reject a verified pending-to-booked transition within seven days. Amount and currency still agree, and either the reference agrees or the counterparty fits. The original fingerprint remains on the booked row so the original pending file still finds it after takeover and deletion. A booked file repeat can also use the current exact or compatible fingerprint. Different pending file fingerprints still stay separate. Migration links are not bank identities.
- The original versioned file fingerprint remains in nullable `fileIdentity` on transactions and tombstones. Only a file import creates it. Migration v18 is accepted by the operator and remains unchanged. Existing rows keep NULL. The fingerprint uses length-prefixed booking day, amount, currency, folded purpose, normalized IBAN or name, source ID, and reference.
- A refresh prefers fitting fetched pending rows within seven days before unfetched file rows. A file import keeps its seven-day closest-day rule. The greedy rule does not maximize pairs. File days 1 and 8 against bank days 7 and 15 leave three rows in every input order. Pending tombstones cannot block booked versions, and a booked source reserves its pending tombstone against unrelated look-alikes.
- Reference-only fallback requires a pending delivery and excludes migrations. A pending refresh cannot take a booked partner by reference alone. Same-state booked fingerprints use IBAN compatibility without the pending-name rule.
- A refresh partner takes bank fields while keeping user fields and row ID. A file partner keeps bank fields and fetched status. A skipped pending file contributes a missing end-to-end reference, so bank-first imports retain its identity too. Only a relaxed file match fills empty user fields; a fingerprint or agreeing-identity repeat cannot restore cleared fields. A booked partner requires an agreeing identity unless the existing exact fingerprint finds it. Unpaired future file rows stay through their dates, including after repeated refreshes. No paired bank row removes another live file row. An expired unmatched pending row follows the existing refresh drop rule.
- A file fingerprint describes an original shape, not a unique occurrence. Fingerprint-only booking transitions go through `Bookings` so identical pending occurrences still need review. Every non-migration booking converts a retained migration ID to its booked prefix before the row is returned.
- `Bookings` checks identity disagreement before a relaxed match. Candidates first narrow to agreeing explicit identities when any exist. Only rows on or before the booked day participate. After preferring agreeing identities, candidates narrow to the nearest day before a unique fetched pending row wins over unfetched file rows. Equal nearest candidates still need review.
- `parse61` takes the booking year from the value year and corrects it by the six-month rule of the spec. It replaces the check for December and January only.

The operator chose seven-day import matching. A stored pending bank rent on 30 November absorbs the 1 December file rent once. For a stored 1 December bank rent and file rents on 1 and 8 December, day 1 pairs and day 8 is imported. For equidistant file days 30 November and 2 December against bank day 1, stable delivered booking day chooses 30 November first, so 2 December is imported, independent of input order.

## Open gate decisions

Migration v18 and seven-day pending import matching are accepted by the operator.

## Risks / Trade-offs

Tasks marked as built in part may differ from the spec in the way their note says.

- A batch entry stays one row, so a rule or a search does not see each payment of the batch on its own. Splitting it waits for the change that also matches the parts against a total, because split parts next to a refresh that brings the total would count the same payment twice.
- A pending batch entry to several counterparties has no name and no IBAN, so its booked version does not book it. After a later file, both rows stay until the user deletes the pending one. A refresh drops the pending row as it drops any pending row that it does not deliver.
- A FUTR row in an offline account stays pending until a booked version arrives or the user deletes it. An offline account has no refresh that drops it after its date.

- `Storage` stores each CSV profile as versioned JSON in the encrypted database. Independent records keep unreadable profiles unchanged when another is saved or deleted. `Import` decodes known column fields and defaults a missing category option to false. Legacy profiles without a delimiter require preview confirmation.
- `Domain` indexes category names and full paths once per file. `Storage` creates, assigns, merges and removes unused file categories in one database transaction, so a failed merge rolls back categories too.

- Cancellation shares a thread-safe flag between the import sheet and the storage transaction. Storage checks it during category writes and before commit. Complete exports carry versioned profile payloads, including unreadable entries, without decoding them.

- Existing rows retain NULL file identity. Without another explicit identity, their prior file history cannot be recovered. A relaxed file match still fills empty user fields, while imports from this build retain their original fingerprint and preserve cleared fields on repeats.
