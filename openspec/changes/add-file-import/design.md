# Design

## Context

This change is part of the first build of the app. The build is a Swift package with the modules `Domain`, `Storage`, `Import`, and `App`, as [ADR 0010](../../../docs/decisions/0010-swift-package-and-macos-15.md) describes. Everything runs on the Mac, with no server ([ADR 0002](../../../docs/decisions/0002-local-first-no-server.md)).

The app keeps all accounts, categories, and transactions of the open database in one in-memory `Ledger` (module `Domain`). Every change goes to the database through `Store` (module `Storage`) and then to the ledger. Views read the ledger. This keeps filters, sums, and charts fast for some ten thousand transactions without queries per keystroke.

## Decisions

The first build follows the spec where the task list marks a task as checked. Open tasks keep the behavior of the spec as the target.

- `TransactionFileImporter.parse` (module `Import`) returns a CAMT entry with the status PDNG or FUTR as pending, on the booking date of the entry, and leaves out an entry with the status INFO. A pending row from a file is booked by `reconcile` (module `Domain`) like one from a refresh, by the rule of `add-account-refresh`: a later file or refresh brings a booked row with the same amount and the same counterparty, at most seven days apart, and `Bookings` pairs it with the stored pending row. The counterparty is the IBAN when both rows have one, otherwise the name. The booking date stays the date of the entry, so the booked version lies within the seven days.
- The CAMT reader builds one transaction per `Ntry` with the amount of `Ntry/Amt`, as the first build does. It does not split a batch into its transaction details. The first build overwrites the name, the IBAN, the BIC, and the references for each `TxDtls`, so a batch takes the counterparty of its last payment. The reader instead collects the values of all details and keeps a counterparty field only when every detail gives the same name and IBAN, and a reference only when every detail gives the same value. It already joins the `Ustrd` purposes of all details.
- The CAMT reader reads the return reason from `RtrInf/Rsn/Cd`. `Transaction` gets the field `returnReason` through a new migration in `Sources/Storage/Schema.swift`. `Transaction(arriving:in:fetched:)` and `takingBankFields(of:)` in `Sources/Domain/Reconcile.swift` copy it, so a stored or booked row keeps it.
- `reconcile` in `Sources/Domain/Reconcile.swift` drops a stored pending row that a refresh does not deliver. It keeps the row when `isFetched` is false and the booking date is on or after `Day(now)`. `isFetched` is false exactly when no refresh delivered or matched the row, so a row from a file needs no new field. A migrated pending row has `isFetched` false as well and follows the same rule. This is an exception to the requirement "Remove a pending transaction that the bank dropped" of `add-account-refresh`, and the spec of this change states it. The bank may deliver its own pending version of the payment with another purpose, and the purpose and the day are part of the fingerprint, so `partners` does not match the two rows. Kept next to it, the file row would count the payment twice, and the booked version would mark both for review. So `reconcile` keeps a future file row only when no delivered pending row `PendingMatch.fits` it: the same amount, the same IBAN or name, at most seven days apart. Every delivered pending row counts, with or without a partner. If the first row that fits has no partner, it takes over the file row through `takingBankFields(of:)`, and the file row goes into `updated` with `isFetched` true instead of the delivered row going into `added`. If its partner is a stored row, an earlier refresh stored the bank's version already, so the file row is dropped. Without this, a refresh before the import would leave both rows, and the booked version would mark both for review. A delivered row whose partner is a deleted row does not count, because the user deleted the bank's version and the file row is the only copy left. Each delivered row takes one file row at most. A file row that only an already taken delivered row fits is dropped, because the bank reported one payment.
- `parse61` takes the booking year from the value year and corrects it by the six-month rule of the spec. It replaces the check for December and January only.

## Risks / Trade-offs

Tasks marked as built in part may differ from the spec in the way their note says.

- A batch entry stays one row, so a rule or a search does not see each payment of the batch on its own. Splitting it waits for the change that also matches the parts against a total, because split parts next to a refresh that brings the total would count the same payment twice.
- A pending row that the bank never books stays pending until the user deletes it, or until a refresh of the account after its booking date no longer delivers it.
