# Design

## Context

This change is part of the first build of the app. The build is a Swift package with the modules `Domain`, `Storage`, `Import`, and `App`, as [ADR 0010](../../../docs/decisions/0010-swift-package-and-macos-15.md) describes. Everything runs on the Mac, with no server ([ADR 0002](../../../docs/decisions/0002-local-first-no-server.md)).

The app keeps all accounts, categories, and transactions of the open database in one in-memory `Ledger` (module `Domain`). Every change goes to the database through `Store` (module `Storage`) and then to the ledger. Views read the ledger. This keeps filters, sums, and charts fast for some ten thousand transactions without queries per keystroke.

## Decisions

The first build follows the spec where the task list marks a task as checked. Open tasks keep the behavior of the spec as the target.

- `TransactionFileImporter.parse` (module `Import`) returns a CAMT entry with the status PDNG or FUTR as pending, on the booking date of the entry, and leaves out an entry with the status INFO. A pending row from a file is booked by `reconcile` (module `Domain`) like one from a refresh, by the rule of `add-account-refresh`: a later file or refresh brings a booked row with the same amount and the same counterparty, at most seven days apart, and `Bookings` pairs it with the stored pending row. The counterparty is the IBAN when both rows have one, otherwise the name. The booking date stays the date of the entry, so the booked version lies within the seven days.
- The CAMT reader builds one transaction per `Ntry` with the amount of `Ntry/Amt`, as the first build does. It does not split a batch into its transaction details. The first build overwrites the name, the IBAN, the BIC, and the references for each `TxDtls`, so a batch takes the counterparty of its last payment. The reader instead collects the values of all details and keeps a counterparty field only when every detail gives the same name and IBAN. For such a batch it keeps a reference only when every detail gives the same value. A batch to several counterparties has no references. It already joins the `Ustrd` purposes of all details.
- The CAMT reader reads the return reason from `RtrInf/Rsn/Cd`. `Transaction` gets the field `returnReason` through a new migration in `Sources/Storage/Schema.swift`. `Transaction(arriving:in:fetched:)` and `takingBankFields(of:)` in `Sources/Domain/Reconcile.swift` copy it, so a stored or booked row keeps it.
- `Domain` owns one `partners` function in `Sources/Domain/Reconcile.swift`. Both file import and refresh call it through `reconcile`. It collects candidate pairs before consuming any row. Delivered pending rows can pair with stored fetched pending rows, unfetched file pending rows, or honored pending tombstones. A pending file repeat can also find its stored booked version without undoing the booking.
- A candidate with conflicting explicit identities is invalid before every other check. Non-NULL file fingerprints, real source IDs, and nonempty end-to-end references are explicit identities. Any disagreement rejects the pair, even if another identity agrees. The file fingerprint is a versioned, length-prefixed string of booking day, amount, currency, folded purpose without whitespace, normalized IBAN (or folded name when absent), normalized source ID, and end-to-end reference. Pending state and user fields are excluded, and no delimiter collision is possible. A bank-first file match learns the fingerprint; a takeover, booking, or tombstone only copies it. An agreeing file fingerprint finds a booked or deleted version after bank dates or purposes change. Migration links are not bank identities. The file reference stays in `endToEndReference`, and a file source ID stays in `sourceID`; a delivery without an identity does not clear either field. `takingBankFields(of:)`, booking, and `DeletedTransaction` preserve them. The original file fingerprint is stored separately in nullable `fileIdentity` on transactions and tombstones. Only a file import creates it. Migration `v18` adds both columns with NULL for existing rows; NULL contributes no identity and keeps existing behavior. The operator must accept this migration in the gate; if declined, booked-repeat guarantees are limited to explicit source IDs or end-to-end references.
- Candidate priority is an agreeing file identity, then an agreeing source ID, then an agreeing end-to-end reference, then a fetched or tombstoned row on the same day that `PendingMatch.fits`, then an unfetched file row with the smallest day distance within seven days. Current or booking source-ID partners precede the already booked versions of pending repeats. Live partners precede tombstones within each category. A pending tombstone is not eligible for a booked delivery. If its source ID arrives booked without conflicting explicit identities, the tombstone can absorb a pending echo with that same ID, but not a new pending look-alike with another or no ID. The function indexes booked identities by source ID before collecting candidates. Reference agreement never overrides conflicting known counterparties: compare IBANs when both exist, otherwise compare known names by the pending-prefix rule, and exact or compatible fingerprints win before reference-only matches. Within each fetched or file priority, an exact fingerprint comes before a compatible fingerprint, and both come before a relaxed match. Fingerprints are same-day matches, so this preserves closest-day choice within the file priority. Pending-to-pending file pairs allow only the same day. An explicit source identity can find an already booked version on another date; an end-to-end reference does so with the same amount. The seven-day limit bounds relaxed matches, not an agreeing identity after successive date changes. Refresh fallback to an unfetched file row requires a covered date on or after today and no review mark. Fetched and tombstoned same-day rows are grouped by day.
- Only valid pairs enter the candidate list. There is no consumed row without a partner. All candidates sort by evidence priority and its specificity, day distance, stable delivered position, then stable stored position. A stable position orders by booking day, creation time, and UUID for live rows; tombstones use their persisted identity fields, fetched flag, deletion time, and optional-value presence, so empty text and a missing field have distinct keys. Live rows precede tombstones on an otherwise equal choice. The function greedily takes a candidate only when neither row is taken. Greedy matching is small and keeps the strongest and nearest evidence; it does not maximize the number of pairs. For file days 1 and 8 December and bank days 7 and 15 December, 7 takes 8 first and three rows remain, regardless of either input order.
- A refresh partner takes bank fields while keeping user fields and row ID. A file partner keeps bank fields and fetched status. A skipped pending file contributes a missing end-to-end reference, so bank-first imports retain its identity too. Only a relaxed same-day file match fills empty user fields; a fingerprint or agreeing-identity repeat cannot restore cleared fields. A booked partner requires an agreeing identity unless the existing exact fingerprint finds it. Unpaired future file rows stay through their dates, including after repeated refreshes. No paired bank row removes another live file row. An expired unmatched pending row follows the existing refresh drop rule.
- `Bookings` checks identity disagreement before a relaxed match. Candidates first narrow to agreeing explicit identities when any exist. Within the remaining candidates, exactly one fitting fetched pending row wins over unfetched file rows, including when they share a reference. Existing ambiguity marking remains when neither rule chooses a unique partner.
- `parse61` takes the booking year from the value year and corrects it by the six-month rule of the spec. It replaces the check for December and January only.

## Open gate decisions

Import matching remains on the same booking day only. A stored bank pending row of -800,00 € on 30 November 2026 and a file row of -800,00 € on 1 December 2026 stay as two rows, totaling -1.600,00 €. Widening the import match to seven days with the closest day first would merge them. The operator still decides whether to widen it.

## Risks / Trade-offs

Tasks marked as built in part may differ from the spec in the way their note says.

- A batch entry stays one row, so a rule or a search does not see each payment of the batch on its own. Splitting it waits for the change that also matches the parts against a total, because split parts next to a refresh that brings the total would count the same payment twice.
- A pending batch entry to several counterparties has no name and no IBAN, so its booked version does not book it. After a later file, both rows stay until the user deletes the pending one. A refresh drops the pending row as it drops any pending row that it does not deliver.
- A FUTR row in an offline account stays pending until a booked version arrives or the user deletes it. An offline account has no refresh that drops it after its date.

- `Storage` stores each CSV profile as versioned JSON in the encrypted database. Independent records keep unreadable profiles unchanged when another is saved or deleted. `Import` decodes known column fields and defaults a missing category option to false. Legacy profiles without a delimiter require preview confirmation.
- `Domain` indexes category names and full paths once per file. `Storage` creates, assigns, merges and removes unused file categories in one database transaction, so a failed merge rolls back categories too.

- Cancellation shares a thread-safe flag between the import sheet and the storage transaction. Storage checks it during category writes and before commit. Complete exports carry versioned profile payloads, including unreadable entries, without decoding them.

- Existing rows retain NULL file identity. Without another explicit identity, their prior file history cannot be recovered. A relaxed same-day match still fills empty user fields, while imports from this build retain their original fingerprint and preserve cleared fields on repeats.
