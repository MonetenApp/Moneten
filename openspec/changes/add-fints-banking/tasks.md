# Tasks

One task per requirement of the spec. A task is checked only when a test or a check in the running app shows the behavior. Issue #13 builds FinTS in three parts: the connector (part 1), the bank accesses in the database (part 2), and the "Add Account" assistant, the refresh commands, the sidebar status, and saved PINs (part 3). "FinTSHelper self-test" is `scripts/build-fints-helper.sh`, which CI runs.

- [ ] 1.2 Identify the app as a registered product. Built in part: the command carries the product ID from Info.plist and the version, verified by FinTSConnectorTests "Asks for the PIN, sends it through the pipe, and lists the accounts". Check the first message with a real bank.
- [x] 1.3 FinTS messages travel over HTTPS only. Verified by FinTSConnectorTests "Refuses an access without https..." and FinTSHelper self-test "plain HTTP refused".
- [ ] 1.4 List the accounts of a login. Built in part: `FinTSConnector.listAccounts`, with the account types verified by FinTSConnectorTests "Asks for the PIN, sends it through the pipe, and lists the accounts". Check with a real bank.
- [ ] 1.5 Use only what the bank allows. Built in part: the helper sends HKSAL, HKCAZ, and HKKAZ only when the account allows them, and fails an account that allows none. The account view comes with part 3. Check with a real bank.
- [ ] 1.6 Fetch the balance separately. Built: the balance is its own order, and a failed transaction order stores the balance and fails the account with the error of the bank in `RefreshResult.transactionFailure`, so its last refresh time stays and the next refresh asks again from that time, verified by FinTSConnectorTests "Maps every field of the result..." and SyncCoordinatorTests "A failed transaction request stores the balance and fails the account..." (#85). Check with a real bank.
- [ ] 1.7 Prefer CAMT over MT940. Built: the helper takes HKCAZ when the account allows it. Check with a real bank.
- [ ] 1.8 A normal refresh asks for at most 90 days. Built in part: the connector asks from the requested day, but no more than 90 days back, verified by FinTSConnectorTests "Asks for the full history first...". The 14 days of overlap are built, verified by BankAccessTests "A first refresh asks for the full history, and a later one from 14 days before the last success" (#85). The note about older transactions is not built.
- [ ] 1.9 The first refresh asks for the full history. Built in part: a request without a first day asks for everything, verified by FinTSConnectorTests "Asks for the full history first...". The fallback to 90 days after a canceled TAN needs a way to cancel one request without the refresh.
- [ ] 1.10 Enforced refresh. Built in part: an enforced request asks for the full history, verified by FinTSConnectorTests "Asks for the full history first...". The commands come with part 3.
- [ ] 1.11 Say when the bank has no older transactions. Built in part: a full-history answer sets `RefreshResult.isComplete`, verified by FinTSConnectorTests "Maps every field of the result...". The message comes with part 3.
- [ ] 1.12 Fetch every part of a long answer. Built by hbci4java, which follows the touchdown point (3040) itself. An answer that stops before the last part fails its account instead of looking complete, verified by FinTSHelper self-test "transactions in part fail the account". Check with a real bank.
- [x] 1.13 Mark pending transactions. Verified by FinTSHelper self-test "CAMT row, pending" and FinTSConnectorTests "Maps every field of the result...".
- [x] 1.14 Store booking date and value date. Verified by FinTSHelper self-test "MT940 row with tagged purpose" and "day in Pacific/Kiritimati", and FinTSConnectorTests "Maps every field of the result...".
- [x] 1.15 Split the structured purpose into fields. Verified by FinTSHelper self-test "MT940 row with tagged purpose" and "CAMT row, pending".
- [ ] 1.16 Join purpose lines. Build it and verify it with a test. Today tagged MT940 lines join without a space, and other lines with one.
- [x] 1.17 Use the end-to-end reference when the purpose is missing. Verified by FinTSHelper self-test "end-to-end reference as purpose" and "placeholder reference".
- [ ] 1.18 Keep the original amount and the deviating party. Needs fields in `Transaction`. Build it and verify it with a test.
- [ ] 1.19 Credit cards through FinTS. Built in part: account types 50 to 59 list as credit cards, verified by FinTSConnectorTests "Asks for the PIN, sends it through the pipe, and lists the accounts". Check with a real bank.
- [ ] 1.20 One dialog for all accounts of a login. Built: one command and one hbci4java dialog for all requested accounts, verified by FinTSConnectorTests "Asks for the full history first...". Check the number of TANs with a real bank.
- [ ] 1.21 Show notices of the bank. Built in part: notices reach `ConnectorReport.notices`, verified by FinTSConnectorTests. The window comes with part 3.
- [ ] 1.22 Show errors in the words of the bank. Built in part: code and text of the bank reach `SyncFailure`, a wrong PIN, a blocked access, or an unregistered app comes first among the errors of an answer, and a failed login fails the access before any order, verified by FinTSConnectorTests "Maps the errors of the bank to failures" and FinTSHelper self-test "the error that needs action" and "login error before any job". Show the code with part 3.
- [ ] 1.23 Handle a PIN change that the bank requires. Build it and verify it with a test or in the app.
- [ ] 1.24 Handle a blocked access. Built in part: 9930 fails the access with `accessBlocked` and never asks for the PIN again. 9931 counts as a wrong PIN, because Sparkassen send it for a wrong login name or PIN; the PIN sheet shows the text of the bank. Both verified by FinTSConnectorTests "Maps the errors of the bank to failures". Skipping it in the automatic refresh comes with issue #40.
- [ ] 1.25 Cancel and interruption. Built in part: a canceled refresh sends cancel to the helper and ends it after 5 seconds at the latest, and a helper that sends nothing for 30 seconds fails the access with a timeout, verified by FinTSConnectorTests "A canceled refresh sends cancel...", "A helper that ignores cancel ends after 5 seconds", and "A helper that stays silent fails with a timeout...". Deferred: keeping "Giro" when the user cancels during "Savings". The helper sends the results only after `execute` of hbci4java returns, so on a cancel no account is complete yet, and a change of `SyncCoordinator` alone keeps nothing. One `execute` per account would send each result early, but it runs a dialog per account against 1.20, and can need a TAN per account. The helper must instead send the result of an account as soon as hbci4java has filled it: hbci4java reports each filled job with `STATUS_SEND_TASK_DONE`, and a job without a pending touchdown point is complete. Then `SyncCoordinator` keeps the results that arrived before the cancel.

## 2. Connector (issue #13, part 1)

- [x] 2.1 `Tools/FinTSHelper`: the hbci4java helper with JSON lines on stdin and stdout, masked diagnostics on stderr, and a passport that stays in memory.
- [x] 2.2 `FinTS`: `FinTSConnector` with `refresh`, `listAccounts`, and `bankInfo`, verified by FinTSConnectorTests over real pipes against scripted helpers.
- [x] 2.3 `scripts/build-app.sh`: the jlink runtime and the jars in `Contents/Resources/FinTSHelper`, signed after the build with the certificate of the app (a Developer ID build leaves the helper out, see 3.2), a secure timestamp, and `allow-jit` for the helper only, and the product ID from the login Keychain in Info.plist. The build fails when the bundled java is not signed like the app.
- [ ] 2.4 Map a CAMT entry that has a booking date with a time only. Deferred: hbci4java reads only the date form of `BookgDt` and `ValDt` and leaves both dates empty. The helper fails such an account with a clear message, verified by FinTSHelper self-test "account without booking date fails alone" and FinTSConnectorTests "A result that does not read fails only its account". Mapping the time form needs the helper to read the raw CAMT document that hbci4java keeps, and to match its entries to the parsed rows. Known gap until then: when only `BookgDt` has the time form and `ValDt` has a date, hbci4java copies the value date into the booking date (`ParseCamt05200108.createLine`), so the helper stores the value date as the booking date and does not fail the account.

## 3. Integration

- [ ] 3.1 Check every scenario of the spec with real banks in a release build, and record the result in the pull request.
- [ ] 3.2 Build with `scripts/build-app.sh developer-id` and check with `codesign -dvv` that the bundled java has the Developer ID authority and timestamp of the app. Deferred: the Mac of part 1 has no Developer ID identity in its Keychain. Known gap: `scripts/build-app.sh` signs the helper with `codesign` after the export, which needs the private key of the Developer ID in the Keychain. A certificate that only Xcode manages in the cloud (ADR 0011) has none, so until this task lets the export sign the helper, `scripts/build-app.sh developer-id` leaves the helper out. That must be solved before the app uses FinTS.
- [ ] 3.3 Check that a bank whose certificate macOS trusts connects, also through a proxy of the macOS settings. The tests prove only the refusal of a certificate that macOS does not trust, because they contact no server.
