# Design

## Context

This change is part of the first build of the app. The build is a Swift package with the modules `Domain`, `Storage`, `Import`, and `App`, as [ADR 0010](../../../docs/decisions/0010-swift-package-and-macos-15.md) describes. Everything runs on the Mac, with no server ([ADR 0002](../../../docs/decisions/0002-local-first-no-server.md)).

The app keeps all accounts, categories, and transactions of the open database in one in-memory `Ledger` (module `Domain`). Every change goes to the database through `Store` (module `Storage`) and then to the ledger. Views read the ledger. This keeps filters, sums, and charts fast for some ten thousand transactions without queries per keystroke.

## Decisions

- `Sources/Import/MoneyMoneyMigration.swift` sends the Apple events for `export accounts`, `export categories`, and `export transactions ... as "plist"` to the running process ID. It finds the installed app and the running process by bundle identifier before each export. A process that quits cannot be launched by the export. macOS asks the user once whether Moneten may control MoneyMoney.
- The exports are flat lists. `indentation` gives the nesting and `group` marks a group. The structure was checked on 2026-11-10 against a real export with 58 accounts and groups, 23 categories, and 30,539 transactions. Only key names, types, and counts were looked at.
- An account has no `iban` or `bic` key. `accountNumber` holds the IBAN and `bankCode` the BIC, so the migration takes a valid IBAN from `accountNumber` and a BIC from `bankCode`.
- `export categories` contains the rule of each category in `rules`. The migration takes it over unchanged. All 12 rules of the real export parse, and replayed over all transactions they pick the category that MoneyMoney shows wherever MoneyMoney applied rules.
- A group carries a balance. MoneyMoney leaves closed accounts out of that sum, but the export has no field that marks an account as closed. A real export showed this for one closed account with a balance other than zero. The migration takes every account over as open and names each group with a different sum in the report, so that the user can mark the closed accounts.
- Booking dates arrive as local midnight and become days in the current calendar.
- A migrated account without a bank access shows its computed balance. Its initial balance is the balance of the source minus the booked transactions of the source in the account currency, so the computed balance ends at the balance of the source. Pending transactions count on top, so 1.000,00 € with a pending -30,00 € shows 970,00 €. A transaction of the source keeps its source identifier. A transaction that the user imported has none, so it counts on top. A pending transaction of the source that a file or a bank booked counts on top as well: it keeps its link to the source in the form `moneymoney-booked:<id>`, so a later run still finds it by the identifier, also when the source books it with another date or purpose. Once the source books it too, the run gives back `moneymoney:<id>`, and the transaction counts as one of the source. A transaction that the user deleted after the booking stays deleted the same way.
- A later run moves the initial balance by the change of the balance of the source minus the change of its transactions. So a correction of the source shows, and an imported transaction, a deleted transaction, and an initial balance that the user typed stay. A transaction that the user deleted counts as one of the source while the source has it. It takes the identifier of the transaction of the source that it keeps out, also one that it matched by its fingerprint, so a transaction that the source has again after a delete in both apps counts again. When the source no longer has it, the run counts it once and the app forgets its source identifier.
- Each transaction keeps `moneymoney:<id>` as its source identifier. The plan finds known transactions with `reconcile`, the rule of refreshes and files, through `Delivery.migration`: the source identifier first, then the fingerprint. So a later run skips a transaction that a refresh or a file stored, and one whose identifier an extension took over. A transaction that was pending and is booked now becomes booked with the bank fields from the source. A transaction that the user deleted stays deleted, also when no refresh had delivered it. An account matches by source identifier first, then by IBAN or by bank code and account number. A migrated account takes the newer balance of the source.
- The plan parses each migrated rule with `Rule(parsing:)`. For a `RuleSyntaxError` it adds a note with the category name, the position, and the message, and it stores the rule unchanged. `Categorizer` skips a rule that it cannot parse, so the category receives nothing through it.
- The plan parses each migrated rule and lists a rule with a term without a field that is an IBAN or an account number. Only the rule-note check requires a SWIFT ISO 13616 registry country and its exact IBAN length before the existing mod-97 check. Creditor IDs and RF references give no IBAN note. A quoted IBAN can have single spaces between groups of four. A term of digits counts as an account number only when a migrated account or the counterparty of a migrated transaction has that account number. Other spacing gives no IBAN note. Account import and file import keep their existing validation.
- A repeat run also checks stored categories with the same source identifier and unchanged rule text in the export. Their notes reach the report through the existing review decision, also when the plan imports nothing. Rules edited in either app and categories matched only by name do not receive these repeat notes.
- The plan lists a migrated rule that has the word and, or, or not without quotation marks and not in capitals, because `Rule(parsing:)` reads it as an operator. The tokenizer of `Sources/Domain/Rule.swift` gives the tokens and character positions through a package interface. The plan and the parser agree on quotation marks and field values. The notes count positions from 1 and include only the affected term, not the full rule.
- The plan lists a migrated rule that has the word true or false without quotation marks, in any letter case, because `Rule(parsing:)` reads it as a rule that matches every transaction or none. It uses the same tokenizer. A word directly after a field operator is a search term, not an operator or constant, so it gives no such note.
- The plan counts the categories whose export entry carries a budget and adds one note for them. The note says that the app did not take the budgets over and promises no later step. A note also says that the app takes the color of each icon and shows its own icons. The check of the real export recorded no budget, so the key is an assumption: the plan counts a `budget` that is a number other than zero, or a dictionary whose `amount` is such a number. A number can also have the form of a balance, `[[200.0, "EUR"]]`. A dictionary without `amount` counts when any of its numbers is not zero, and a true or false value is no number. Check the key names of a category with a budget in a real export before task 3.1.
- Migrated categories count as assigned by hand.
- When the database has no transactions yet, the plan leaves out the starter categories, and they are removed after the user confirms the import. Categories the user made stay.

## Refreshes during migration

`Sync` pauses new refreshes and waits for the running refreshes, including their final state and account writes, before the migration transaction starts. The app disables new manual refresh commands while storage runs. Due automatic accounts stay due for the next tick. No untracked task can restart a command after "Cancel Refresh". The coordinator awaits its final account callback before releasing an access. Queued refreshes resume after the pause. This keeps synchronous bank writes from waiting behind the migration writer on the main actor.

Menu commands, Settings, and extension management stay disabled during storage, and only then: a file import or an export does not disable them, while Lock and cancellation remain available. Storage also waits for an existing extension installation to finish; new installs wait for the next update pass after migration. Catalog persistence uses an async database write, so a download finishing during migration cannot block the main actor. Catalog checks run one at a time and publish only into the store they started with.

The preview retains the cached exports and calendar. Inside its write transaction, `Storage` reads the current ledger and deleted rows and rebuilds the plan with `Import` before saving anything. The assistant reports this rebuilt plan, so a refresh after the preview cannot add a duplicate or lose newer bank fields or user edits. The same cancellation flag covers rebuilding and writing. When the app locks during storage, it cancels first and closes that store in background work so a database read or rollback cannot block the lock screen.

The shared `Domain` reconciliation keeps its full-account matching scope and accepts a throwing checkpoint. Stored and deleted fingerprint indexes check it too. Matching index construction publishes a zero completed count and checks cancellation. Row reconciliation then publishes completed counts. Existing callers use its nonthrowing entry point.

## Progress and portfolio exports

`Import` owns a typed progress value with a step, completed count, optional total, and optional account name. Its publication decision is a pure function of the previous value and elapsed time. A new account waits for the second like a new count, because an export sorted by date changes the account on nearly every row. Row loops check cancellation and report at least once per second, on a step change, and on completion. The app consumes these updates on the main actor. Parsing, reconciliation, saving, ledger loading, and report building run in background work. Cancellation propagates to that work. The storage transaction checks cancellation between writes and before commit and includes starter category replacement. A cancel of the task only sets the cancel token, so GRDB never interrupts a statement of the migration. A rollback of thousands of rows can move `PRAGMA data_version` although no other program wrote, so `Store.write` lets the disk watch record the version after its own rollback, before any other access. Its last check seals the cancel. A later Cancel is refused and does not cancel the task, because a task cancel would still abort the commit in the database. The assistant then stays open and shows the report.

The source returns each complete export in one Apple event. It provides no intermediate counts. The assistant shows a waiting message until it can read the total. It does not infer progress from file size or elapsed time. The debug harness logs step codes and integer counts only.

The research documents `export portfolio` with account and asset class parameters and a property-list result. Neither the research nor `Fixtures/moneymoney` records its root shape, position key names, account link, units, price currency, or purchase-price encoding. The extension fixtures describe a different interface and are not evidence of AppleScript export keys. The migration does not guess a parser or request that export. The existing account balance and portfolio history come over. Each exported portfolio gets an explicit not-migrated note on every run, even when it matches an existing account. The note of a portfolio without a bank access asks to connect it, and the note of a connected one says that its bank access fetches the positions. Existing bank positions stay unchanged. Task 1.15 records the operator step required before position import can be built.

## Risks / Trade-offs

- The tests use synthetic exports with the structure of the real export. No real names or amounts are in the repository.
- A transaction can have another currency than its account, for example USD on a EUR account. Sums over such transactions add their amounts without conversion. Foreign currencies get their own change.
