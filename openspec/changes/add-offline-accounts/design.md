# Design

## Context

This change is part of the first build of the app. The build is a Swift package with the modules `Domain`, `Storage`, `Import`, and `App`, as [ADR 0010](../../../docs/decisions/0010-swift-package-and-macos-15.md) describes. Everything runs on the Mac, with no server ([ADR 0002](../../../docs/decisions/0002-local-first-no-server.md)).

The app keeps all accounts, categories, and transactions of the open database in one in-memory `Ledger` (module `Domain`). Every change goes to the database through `Store` (module `Storage`) and then to the ledger. Views read the ledger. This keeps filters, sums, and charts fast for some ten thousand transactions without queries per keystroke.

## Decisions

The first build follows the spec where the task list marks a task as checked. Open tasks keep the behavior of the spec as the target.

### Balance of an offline account

`Domain` owns the balance. `Ledger.computedBalance` adds the initial balance and every row of the account in the account currency, pending rows included except those with `review != nil`, as the changes `add-charts` and `add-account-refresh` decide. `Account.isInBalance` calls `Transaction.isInSum(of:)`. #139 adds both, and `Transaction.isInSum(of:)` holds this test. It is the same function that the balance chart starts from, so the sidebar and the last bar agree. Once splits exist, the parts count and the original does not, as the change `add-split-transactions` defines. A new offline account has an initial balance of 0, and the account settings of the change `add-account-management` change it.

### One signed amount

The transaction window in `App` has one amount field. `AmountParser` in `Domain` reads the text with its sign, and the window stores that value as it is. The window has no choice between money in and money out, so no switch can flip a typed sign.

### The window for a manual transaction

`TransactionDraft` in `Domain` holds the typed name, amount, purpose, and category, so that a test checks the rules of the window. `amountMinor(in:region:)` refuses an empty field, text that `AmountParser` cannot read, an amount with more decimal places than the currency has, and an amount that rounds to zero in the currency, each with its own message under the amount field.

The amount field reads the text with both decimal marks through `AmountParser.decimal(from:decimalMark:)` and drops a reading whose value needs more decimal places than the currency has. So "1.234" is 1.234,00 € and "1,200" is 1.200 JPY. Two different readings remain only for a currency with three decimal places, such as "12,345" in KWD, and then the decimal mark of the region of the Mac wins, which `DecimalMark(region:)` reads from the locale. The field strips the code and the symbol of the account currency first, so "12.50 $" reads in an account in US dollars. Text that has no reading within the places of the currency, such as "4,8051" in euros, gets its own message and never rounds.

`Ledger.newTransactionDraft(in:selection:)` picks the template: the one selected row of the account, also a part of a split. A row in the currency of the account fills the name, the amount, the purpose, and the category. A row in another currency fills no amount, because the window stores the amount in the currency of the account and would change its value. `AmountParser.editableText(_:decimalMark:)` writes the amount with every decimal place of its currency and a decimal comma, such as "-12,00", for the template and for editing.

`Ledger.nameSuggestions(for:)` lists one earlier row for each name that starts with the typed text, newest first. It compares the folded name at the start of the search text of each row, which the ledger keeps already, so a keystroke stays within a frame with 50,000 names. The typed text gets the same single spaces as the search text. The window keeps the suggestions in its state and searches again only when the name changes, never on a redraw. `TransactionDraft.enterName(_:offered:for:in:)` fills the purpose and the category, while they are empty, only when the new name is one of the suggestions shown for the earlier text and did not grow by one typed character, because the suggestion list of the system reports no choice of its own. Typing a name to its end fills nothing, and a chosen suggestion that adds only one character fills nothing either: after "Kiosk ", choosing "Kiosk 7" looks the same as typing the 7, so the purpose and the category stay empty. After "Kiosk", the same choice fills them. A filled category restricted to other accounts stays out.

### Manual transactions in an account with bank access

"Add Transaction..." works in every account except a portfolio, whose value comes from its positions. The window marks each new row with `Transaction.isManual`, which migration `v23` stores in `bankTransaction.isManual` and a complete export writes as the optional key `isManual`. GRDB applies the migrations in the order of registration, so `v23` comes after `v24` and after any migration that lands on main before this change.

`reconcile` leaves manual rows out of the pairing of a refresh. Without that, a manual row of -12,00 € "Kiosk" and a delivered row of -12,00 € "KIOSK" on the same day paired by their fingerprint: the manual row took the source ID of the bank, and the delivered row was lost. A file import and a migration still pair manual rows, so a file of the same cash rows adds no copies. `Store.deleteTransactions` keeps no record of a deleted manual row, because no source delivers it, so such a record could only keep out another booking. A file that matches a manual row gives it the `fileIdentity` of the matching file row, and a migration gives it its `sourceID`. From then on the row is a row of that source, which `Transaction.isOnlyManual` tells apart: a refresh pairs it, deleting it keeps a record, so a refresh that delivers the same booking after a delete adds nothing, and the window treats it as a row of that source. Without the pairing, a refresh after the file added the booking of the bank beside the matched row and counted it twice. A file import still brings the row back, as it brings back every deleted row that no refresh delivered (`DeletedTransaction.wasFetched`). Without the file identity, a CSV row of -12,00 € "KIOSK" that matched a manual row of -12,00 € "Kiosk" left no record, and a refresh after the delete added the booking again. The initial balance that a refresh derives counts manual rows, matched or not.

"Edit Transaction..." follows `add-transaction-list` (task 1.16): `Ledger.editsFields(of:)` offers the date, the value date, the name, the amount, and the purpose of every row except a part of a split, and `Transaction.edit(_:)` keeps the values of a source in `Transaction.original`, so that the next refresh still finds the row. A manual row that no source matched has no source values, so it takes the corrected values and records no `original`, stays `isOnlyManual`, and keeps no record when the user deletes it. A derived initial balance follows the edit by the rule below. An earlier version of this change allowed fewer fields in an account with bank access, because a changed row from a file was added again by the next refresh. `original` solves that for every source, so the restriction went in the merge with #275. An amount of zero is refused only for a manual row: a row that a source delivered with zero keeps it when the user changes another field.

The sidebar shows the balance that the bank reports, and every row booked by the day of that balance is part of it, a manual row as well as a row of a source. While `Account.initialBalanceIsDerived` says that a refresh derived the initial balance, one rule of the change `add-charts` holds: the initial balance is the last bank balance less `Account.bookedSum(of:through:)` of all live rows of the account at the day of that balance. `Ledger.followingBankBalance(saving:deleting:)` applies the rule to the rows that the app is about to save or delete, so `AppModel.commit` and the delete command store the account in the same write as the rows, for an added, edited, or deleted row and for an offsetting entry. `reconcile` applies it after a refresh and a file import. The computed balance, the charts, and the header keep ending at the bank balance, and a manual row before that day only shapes the history before it. A manual row after that day counts on top until a refresh reports a balance of its day or later. Then the bank balance holds it, whether the bank delivered a booking for it or not.

An earlier version moved the initial balance by each changed manual row and moved it again when a refresh passed a planned row. Two cases came out wrong. A bank that reports only a balance delivered no booking for a planned -50,00 € row, and the move left the computed balance at 100,00 € against a bank balance of 50,00 €. A manual row that moved the value when the user added it, and that a file matched later, no longer moved it back on delete, so the computed balance was off by its amount. The project lead replaced the moves by the rule, which has no history to get wrong.

An initial balance that the user entered, in the account settings or with "Calibrate", never changes: `Account.enterInitialBalance(_:)` clears `initialBalanceIsDerived`, because the user chose that value. The difference to the bank balance is then for the calibration proposal. Before the first refresh the initial balance is not set, and the first refresh derives it with the manual rows. Migration `v23` adds `account.initialBalanceIsDerived` as false for every account, because the database does not tell a derived value from an entered one. An existing account therefore keeps its value, and a manual row there shows the calibration proposal instead.

### Offsetting entry

`Domain` builds the offsetting entry from the source transaction, the source account, and the target account, so that a test can check every field. The entry is a manual transaction with `isManual`, so no refresh of the target account pairs it. It takes the name, the purpose, the comment, and the category of the source, and the booking date of the source as its booking date and value date. A copied category gets `categorizedBy` `.manual`, because `Categorizer.categorize` keeps only a manual category and would otherwise move a copied rule category, or clear it when no rule matches. A source without a category gives `categorizedBy` `.none`, so that the rules run on the entry. The IBAN and BIC of the source account become `counterpartyIBAN` and `counterpartyBIC`. `Transaction` has no fields for an account number and a bank code, so a source account without an IBAN gives no counterparty account. A category whose restriction does not include the target account is dropped, and then the categorization rules run on the entry, which has `categorizedBy` `.none`. No link joins the two rows, so an edit of one changes only that row.

The entry is always booked. A refresh never books a transaction of an offline account, so a pending entry would stay pending. A selected part of a split transaction is a row of its own: the user picks it in the view of its category, so the entry takes the amount, the category, and the comment of the part. Only open offline accounts are targets, because the user no longer keeps the money of a closed account in it. The one amount whose opposite does not fit into `Int64`, which a complete import accepts, stops the whole choice before anything is written, and the app says why. The menu has no undo: the user deletes an unwanted entry in its account.

The entry keeps the currency of the source, and the balance of an offline account counts only rows in its currency. So `Domain` also names the offline accounts that can take the entries of the selected rows: those in the currency of every selected row. The menu in `App` disables the others. A conversion would need a rate, and the app converts no currencies.
