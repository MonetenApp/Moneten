# Tasks

One task per requirement of the spec. A task is checked only when a test or a check in the running app shows the behavior.

## 1. Requirements

- [x] 1.1 One row per transaction. Verified by the debug harness snapshot in the first build.
- [x] 1.2 Newest transactions first. Verified by LedgerTests "Newest first".
- [x] 1.3 Details from the bank. Verified by TransactionCopyTests ("The details of a row come in a fixed order and leave out what has no value", "An empty text from the source counts as no value") and by the debug app check `details`: a made-up direct debit with all eight details has a help tag with the two lines of its purpose, then the eight details in the order of the spec; its transaction sheet lists the transaction type, the return reason AC04, the end-to-end reference, the mandate reference, the creditor ID, the IBAN in groups of four, and the BIC, with the value date as a field above, in light and dark mode; and every visible row of "Girokonto" stays 55 points high. `Transaction` has no receipt date. The original amount in a foreign currency and the deviating originator or recipient come with task 1.18 of `add-fints-banking`, which adds them to `Transaction`.
- [x] 1.4 Account name in group and category views. Verified by the debug harness snapshot of the group "Private" with two rows selected: each names "Girokonto" at the end of the line with the payee; with "Group transactions by account" on, the heading "Girokonto" stands above its rows (debug harness `groupbyaccount Private`).
- [x] 1.5 Pending transactions look different. The hatching is verified by the debug harness snapshot: the row is hatched across all cells, and the header shows "Pending" with the sum of the pending transactions of the view and nothing without them. The sum leaves out a pending transaction marked for review, verified with task 1.30 of the change `add-account-refresh`.
- [x] 1.6 New transactions are marked. Verified by a dot in the row, see the debug harness snapshot in the first build.
- [x] 1.7 Text can be selected and copied. Copy of a selected word goes to the field editor of the text, which is the first responder. In a first run of the debug harness, a double click on the name of the first row selected "Max" in a text view, and Copy put exactly that word on the pasteboard. The Mac was locked during the later runs, and macOS then did not start the field editor for a synthetic click, so the check `textmenu` could not repeat it. Copy of whole rows is task 1.23.
- [x] 1.8 Several rows can be selected. Verified by the table allows a multiple selection.
- [x] 1.9 The context menu acts on the selection. Verified by the menu receives the selected rows.
- [x] 1.10 Checkmarks. Verified by checkbox column; LedgerTests use the status filter.
- [x] 1.11 Mark all transactions as checked. Verified by reading `AppModel.markAllChecked`: it counts the unchecked rows of the view and their accounts, asks, and changes nothing on "Cancel". Not covered by a test, because the app has no test target yet.
- [x] 1.12 Checkmarks can be hidden. Verified by the debug app check: "Checkmarks" in the View menu is a toggle on `AppModel.showsCheckmarks`. With the harness command `checkmarks off` no row of "Girokonto" shows a checkmark control, in light and dark mode, and after a restart of the app with the same database the controls stay hidden. The stored checkmarks do not change.
- [x] 1.13 Comments. Verified by "Add Comment..." with ⇧⌘K and a note icon in the row.
- [x] 1.14 Daily balance in the list. Verified by DayEndBalanceTests (the scenario "Turn on" with 1.200,00 € and two rows of -50,00 € and -25,00 €, and a search that hides a row of the day) and by the debug app check: with "Daily balance" on, the top row of each day of "Girokonto" shows the balance at the end of that day below its amount, and the newest one equals the balance of the header, 16.898,33 €. The snapshot of the group "Private" has no switch in the filter bar. That "Daily Balance" in the View menu is disabled without a selected account is read in `AppCommands`, because the Mac was locked and SwiftUI kept every menu disabled. The perf scenario "daily-balance-in-account" turns it on in 74 ms.
- [x] 1.15 Go to the account or the category. Verified by "Go to" in the context menu.
- [x] 1.16 Edit a transaction. Verified by EditTransactionTests (a corrected purpose, a changed day and amount, a source with IDs that changes other fields, an edit back, a second edit, a deleted edited row, and an edited pending row that the bank books), MergeTests "An edited transaction keeps its values in the database...", AllDataTests "A complete export imports into an empty database...", which holds an edited row, and the debug app check: "Edit Transaction" of a fetched row offers the date, the value date, the name, the amount, and the purpose; after the purpose "Coffee with a client" the next refresh added 0 rows and the row kept the purpose (harness commands `fetch first` and `edit`). Round 2 of #275 adds EditTransactionTests for an edited pending row that a refresh delivers again, a booked version of an edited amount, a bank amount change on an edited split, a split part that offers only its category and comment, and an amount without a magnitude. Round 3 adds EditTransactionTests for a future file row that the edit moved into the past, with and without the bank's row, a row typed in by hand that a CSV file finds by its corrected amount, and `Money(fitting:currency:)`, FileImportTests for too large amounts in CSV, CAMT, and MT940, FinTSConnectorTests and MoneyMoneyMigrationTests for a too large amount from the bank and from a migration, and AllDataTests for a transaction amount without a magnitude.
- [x] 1.17 Delete transactions. Verified by "Delete Transaction..." with the warning that deleted transactions cannot be restored, offered only in an account view (`TransactionMenu`). Not covered by a test, because the app has no test target yet.
- [ ] 1.18 Services for selected text. Built without code of its own: a double click on text in a row starts the field editor of that text, a text view, and a right click on the selected word opens the context menu of the text view instead of the menu of the table. In a first run of the debug harness, that menu held "Look Up", "Translate", "Copy", and "Share…" for the word "Max", and the menu of the table did not open. The Services entries could not be seen: the Mac was locked, and macOS added none to the menu of a plain AppKit text view in the same session either. Verify it with the harness command `textmenu` on an unlocked Mac, which logs `services=true` when the menu holds the Services, or with a right click on a selected word.
- [x] 1.19 Empty states. Verified by the debug harness snapshot in the first build.
- [ ] 1.20 The list stays fluid with a large history. Built in part: the perf scenarios "scroll-large-group" (50,000 rows from top to bottom in 20 steps, 50 ms, every visible row has its view after each step) and "daily-balance-in-account" (74 ms) pass. "select-all-in-large-group" takes 946 ms, over the half second of the budget: a sample shows that `NSTableView selectAll:` asks the SwiftUI table coordinator `shouldSelectItem` for each of the 50,000 rows, and the code of the app takes a few milliseconds of it. The other scenarios that are slow on this branch are slow on main as well (issue #51).
- [x] 1.21 Row layout. Verified by the snapshots of the debug harness commands `seed` and `history` in light and dark mode, with two rows selected.
- [x] 1.22 A sum of zero has the currency of the view. Verified by `MoneySums.shownAmounts` and the LedgerTests test "A sum of zero has the currency of the view, also when every row is under review or the list is empty" (issue #213).
- [x] 1.23 Copy selected rows as text. Verified by TransactionCopyTests (the scenarios "Copy a row", "Copy two rows", "Text that a spreadsheet would read as a formula" for "=", "+", "-", and "@" also after leading whitespace, and "Account number and BIC", plus the order of the details in the purpose, whitespace, a missing name, and amounts and dates in de_DE, en_US, en_GB, de_CH, and fr_FR) and by the debug app check `copyrows`: with 1, 2, and 3 selected rows of "Girokonto" and of the group "Private", the action of Edit > Copy on the focused table put 1, 2, and 3 lines of 6 tab-separated fields on the pasteboard, equal to `TransactionCopy.text`.
